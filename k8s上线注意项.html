一、未完善清单（按阻塞等级）

P0 上线阻塞不解决不能上线

1. 镜像仓库地址是占位符，且缺 imagePullSecrets

位置：k8s/base/kustomization.yaml 引用的 deployment.yaml（registry.example.com/mycut/web:IMAGE_TAG）、两个 overlay 的 images 段

影响：Pod 拉不到镜像，直接 ImagePullBackOff。

动作：① 改成 GitLab 容器仓库真实路径（如 gitlab.sunwin-sh.com/development/mycut/web，overlay 里 kustomize edit set image）；② 私有仓库需在两个 namespace 各建 docker-registry 类型 Secret 并在 deployment patch 加 imagePullSpec.imagePullSecrets；③ 推镜像用 CI 账号 token。

2. test 环境 Ingress 没有 TLS —— 这会让整个编辑器不可用

位置：k8s/overlays/test/ingress.yaml（cert-manager 注释被注释、host 是占位域名）

影响：编辑器的 WebCodecs 解码（封面图、时间线预览、播放帧）与 OPFS 存储（navigator.storage）都是安全上下文专属 API。HTTP 域名下：素材能入库但没有封面、预览/播放直接报错——本次本地排查已实际复现。

动作：① 打开 cert-manager 注解（letsencrypt-prod issuer 视集群实际配的 issuer 名）并加 tls: 段；② host 换成真实 test 域名并配 DNS；③ 上线验收用 https 域名打开编辑器，导入视频确认封面与预览正常。

3. 站点域名全部是占位符（ConfigMap + Ingress host）

位置：两个 overlay 的 kustomization.yaml（https://test.mycut.example.com / https://mycut.example.com）、ingress host

影响：NEXT_PUBLIC_SITE_URL 是 better-auth 的 baseURL、受信 origin 和 Cookie 域的根——域名不一致会导致登录失败 / 会话 Cookie 异常。

动作：改成真实域名，保持 ConfigMap、Ingress host、DNS 三者一致；若还要通过别的入口（IP/备用域）访问，需给 Deployment 加 TRUSTED_ORIGINS 环境变量（代码已支持，逗号分隔）。

4. migrate Job 无法重复执行，发布编排缺失

位置：k8s/base/migrate-job.yaml（在 base resources 里，随 apply -k 创建）

影响：Job 创建后不可变，第二次 apply -k 报 field is immutable，发布流程卡住；且没有任何机制保证"新版本 Pod 就绪前迁移已完成"——迁移滞后于新代码会出现 SQL 报错窗口。

动作：发布脚本中固定执行 kubectl delete job mycut-migrate -n <ns> --ignore-not-found && kubectl apply -k k8s/overlays/<env>，并 kubectl wait --for=condition=complete job/mycut-migrate 成功后再观察 rollout；远期可在 CD（GitLab CI）里编排为独立 stage。

5. prod 的 Secret 还是占位骨架

位置：k8s/secrets/prod.yaml（全部 CHANGE_ME，gitignored）

影响：直接 apply 会导致服务连不上库 / 认证不可用 / 渠道密钥加密失效。

动作：prod 独立 PG/Redis 就绪后生成三把独立密钥（生成命令已写在 prod.yaml 注释里），重新录入渠道 API Key。禁止复用 test 的 BETTER_AUTH_SECRET/MODEL_CREDENTIALS_KEY。

P1 上线前应完成不阻塞但强烈建议

6. 无监控与日志接入

Deployment 没有 Prometheus prometheus.io/scrape 注解，也没有 ServiceMonitor/PodLog 采集配置。动作：至少接入 ingress-nginx 指标 + 容器 stdout 日志采集；关键告警：Pod restart 激增、readiness 摘除、Job 失败、证书到期前 14 天。

7. prod 应使用独立 Redis，test 与本地共用的现状要知晓

当前本地开发与 test 共用同一 Redis 实例（同 db0）：滑动窗口限流 key（rate-limit:*）互相计数、互相影响。test 阶段可接受；prod 必须独立 Redis（或规划独立 db 号 + key 前缀）。

8. 镜像 tag 是浮动 tag（test-latest / prod-latest）

同一 tag 被覆盖后，"回滚到上一版"无从谈起，且节点上缓存的 old-latest 会造成版本不一致。动作：CI 产出不可变 tag（git sha 或日期+sha，如 test-20261104.abc1234），kustomize 同步改 tag；latest 只作游标参考。

9. 外部数据层的备份与恢复演练没有着落

PG/Redis 在集群外，k8s 的任何备份机制都覆盖不到。动作：PG 每日全备 + WAL 归档，恢复流程至少演练一次；Redis 可容忍丢失（限流/临时状态），但要确认没有业务数据只存 Redis。素材视频本体存用户浏览器（IndexedDB/OPFS），服务端没有副本，用户换浏览器/清缓存即丢——运营口径要提前告知。

P2 知晓即可运行期留意

10. readiness 探针直连数据库

readiness 用 /api/health/deep（真实连 PG），DB 抖动会摘除流量——这是设计意图，但故障排查时要知道"流量掉了"可能是数据库的事。

11. HPA 用内存均值 75%

Next SSR 内存抖动较大，容易频繁扩缩容；建议观察一段时间后考虑换 CPU 指标或调阈值。

12. 密钥轮换语义（务必写进运维手册）

BETTER_AUTH_SECRET 轮换 → 全部用户会话失效（重新登录即可，无数据损失）；MODEL_CREDENTIALS_KEY 不可丢失也不可随手换——丢了库里加密的渠道密钥全部解不开，只能在管理面板逐个重录。改 Secret 后必须 kubectl rollout restart deploy/mycut-web（Secret 更新不会自动重启 Pod）。

13. 多副本下的后台任务已做防护

任务惰性同步已加 PG advisory lock，HPA 扩到多副本安全；每个客户端每 5 秒轮询一次 /api/ai/tasks，副本多时轮询量线性增长，量大后建议加服务端缓存。

二、运维操作手册

首次部署顺序（每环境）

  1. 建 namespace（mycut-test / mycut-prod）
  2. 建镜像拉取凭证（若仓库私有）
  3. kubectl apply -f k8s/secrets/<env>.yaml（先于一切工作负载）
  4. 修正 overlay：真实镜像 tag、真实域名（ConfigMap + Ingress host + TLS）
  5. 跑 migrate Job 并等待 Complete
  6. kubectl apply -k k8s/overlays/<env> → rollout → 验证
  7. 验收：curl https://<域名>/api/health/deep 返回 ok；浏览器登录、生成任务、素材封面/预览正常（https 下）

日常发布 SOP

# 1. 推不可变 tag 镜像（CI 产出）
# 2. 跑迁移（删旧 Job 重建，等待完成）
kubectl delete job mycut-migrate -n mycut-test --ignore-not-found
kubectl apply -k k8s/overlays/test
kubectl wait --for=condition=complete job/mycut-migrate -n mycut-test --timeout=300s
# 3. 更新镜像 tag 并发布
cd k8s/overlays/test && kustomize edit set image registry.example.com/mycut/web=gitlab.sunwin-sh.com/development/mycut/web:test-20261104.abc1234
kubectl apply -k .
kubectl rollout status deploy/mycut-web -n mycut-test
# 4. 验证
curl -s https://test-域名/api/health/deep
# 回滚：kubectl rollout undo deploy/mycut-web -n mycut-test（或改回旧镜像 tag 重新 apply）

监控与告警检查点

Pod 层

CrashLoopBackOff 高频原因：env zod 校验失败（缺/错 DATABASE_URL、REDIS_URL、密钥格式不对——MODEL_CREDENTIALS_KEY 必须 64 位 hex）；OOMKilled（limit 1Gi，Next 高峰注意）；启动期 30×2s startupProbe 内未就绪会被杀。

流量层

readiness 摘除 ≈ PG 连不通；5xx 激增看渠道上游（fal/ark 等外部依赖）；限流 429 与 Redis 连通性直接相关（调用方 fail-open，Redis 挂掉只丢限流不拦请求）。

数据层

PG 连接数：实例数 × PGPOOL_MAX(10) 必须低于服务器 max_connections；慢查询关注 credit_ledger / generation_tasks 的时间线查询（已建索引）。

证书与域名

cert-manager 续期（letsencrypt 90 天）；域名到期、DNS 指向变更；test 无 TLS 状态下禁止给用户开放使用。

密钥与配置管理纪律

  1. 真实凭据只存在于 k8s/secrets/（gitignored）和集群 Secret 中；模板 k8s/secret.example.yaml 进 git
  2. 本地 apps/web/.env.local 与 test Secret 必须同步修改（共用同一库：两处密钥不一致会导致会话互踢、渠道密钥解密失败）
  3. 所有连接串里的特殊字符按 URL 编码书写（`→%60、/→%2F、&→%26），这是本库密码踩过的实际坑
  4. prod 三把密钥独立生成；MODEL_CREDENTIALS_KEY 单独安全备份（密码管理器/保险箱），丢失 = 渠道密钥全部重录
