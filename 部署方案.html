2. 为什么是 Node 多机（而不是 Cloudflare）

仓库里保留了 opennextjs-cloudflare 的 preview/deploy 脚本，但多机部署应走 Node/Docker 路线，原因在代码里：

  • 数据库驱动是 postgres.js（src/db/index.ts），Redis 客户端是 ioredis（src/services/redis.ts）——两者都是 TCP 长连接，Cloudflare Workers 运行时不支持 outgoing TCP，这套代码在 CF 上跑不起来；
  • next.config.ts 已配置 output: "standalone"，构建产物自带最小 Node 运行时入口，天然适配容器。
注意若将来要上 Cloudflare，需要把限流换成 HTTP 版（Upstash REST）、数据库换成 HTTP 网关或 D1，改动不小。本文不覆盖该路线。

3. 环境变量清单（关键）

定义在 src/env/web.ts（zod 校验，缺失即启动失败）。多机部署的核心纪律：所有实例的每一项配置必须完全一致，尤其是两个密钥。

变量要求说明
DATABASE_URL所有实例相同指向共享 Postgres。postgres://user:pass@host:5432/appdb
REDIS_URL所有实例相同指向共享 Redis。限流 fail-open（auth/rate-limit.ts）：Redis 不可用时请求放行，不会拖垮接口，但要意识到这时没有限流。
BETTER_AUTH_SECRET所有实例相同，且必须换强随机签名 better-auth 会话 + 管理员提权 cookie（HMAC，auth/guard.ts）。当前开发环境是弱密钥（每次启动都有 better-auth 警告日志）。上线时生成：node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"。换密钥会使全部会话与提权状态失效（重新登录即可）。
MODEL_CREDENTIALS_KEY所有实例相同32 字节 hex，AES 加密存进数据库的渠道 API 密钥（services/admin/secrets.ts）。任一实例密钥不同 → 该实例解不开渠道密钥，AI 生成在它上面全部失败。该密钥必须随数据库一起备份（见第 10 节）。
NEXT_PUBLIC_SITE_URL所有实例相同正式域名（如 https://cut.example.com）。better-auth 的 baseURL 与 trustedOrigins 都取它；开发默认 localhost，不改会导致登录回调被拒。
PGPOOL_MAX可选（默认 10）每实例 Postgres 连接池上限（postgres.js max，db/index.ts）。实例数 × 池大小必须小于 PG 的 max_connections（默认 100）；扩超过 8 台时调小此值或上 PgBouncer。
NODE_ENVproduction—
NEXT_PUBLIC_MARBLE_API_URL
MARBLE_WORKSPACE_KEY
FREESOUND_CLIENT_ID

4. 应用容器化

利用 output: "standalone"。在仓库根目录建 Dockerfile：

FROM node:22-alpine AS build
WORKDIR /repo
COPY package.json package-lock.json ./
COPY apps/web/package.json apps/web/
RUN npm ci
COPY . .
RUN npm run build --prefix apps/web
# standalone 产物在 monorepo 下位于 apps/web/.next/standalone/apps/web/

FROM node:22-alpine
WORKDIR /app
COPY --from=build /repo/apps/web/.next/standalone/apps/web ./
COPY --from=build /repo/apps/web/.next/static apps/web/.next/static
COPY --from=build /repo/apps/web/public apps/web/public
ENV NODE_ENV=production PORT=3000
EXPOSE 3000
HEALTHCHECK --interval=15s --timeout=3s CMD wget -qO- http://127.0.0.1:3000/api/health || exit 1
CMD ["node", "server.js"]
注意standalone 在 monorepo 里的嵌套路径以实际构建结果为准（构建后看 apps/web/.next/standalone/ 下 server.js 的位置），上例按当前目录结构给出。改动后先在本机跑一次容器验证再推镜像。

构建与运行：

docker build -t mycut-app:1.0 .
docker run -d --name mycut-app \
  --env-file /etc/mycut/app.env \      # 第 3 节的全部变量
  -p 3000:3000 mycut-app:1.0

/api/health 返回 200 "OK"（api/health/route.ts），用作存活探针；/api/health/deep 会执行 select 1，不可达数据库时返回 503——把 LB 的健康检查指到 deep 版本，即可自动摘除"进程活着但连不上数据库"的节点。

5. 基础设施：Postgres 与 Redis

Postgres

  • 版本 ≥ 14，编码 UTF8（现库即 UTF8，直接 pg_dump/restore 迁移上生产）。
  • 连接数预算：postgres.js 默认每实例 max 10 连接，Postgres 默认 max_connections=100 → 默认配置下不要超过 ~8 个应用实例。扩更多时：在 db/index.ts 给 postgres(url, { max: 5 }) 设小池，或前面加 PgBouncer。
  • 表都在 app schema 下（src/db/schema.ts），备份/恢复按整库即可。

Redis

  • 用途只有两类：better-auth 限流（key 前缀 ba-rate-limit:）与 IP 滑动窗口限流（sorted set，带 TTL）。
  • 数据可丢：重启/清空只影响限流窗口与登录尝试计数，不丢业务数据。无需持久化配置，单机 Redis 即可起步。

最小化起步可以用一台基础设施机跑 compose：

services:
  postgres:
    image: postgres:16-alpine
    environment: [POSTGRES_DB=appdb, POSTGRES_USER=appuser, POSTGRES_PASSWORD=…]
    volumes: [pgdata:/var/lib/postgresql/data]
  redis:
    image: redis:7-alpine

规模上来后再换成托管数据库 + 托管 Redis，应用侧只需改两个连接串。

6. 数据库迁移与首次启动顺序

重要迁移只能由一个主体对共享库执行，绝不能每台实例启动时各跑一遍。
  1. 开发库与生产库的现状：当前开发库是 drizzle-kit push 直接推出来的，没有 __drizzle_migrations 记录。若生产库沿用同一份 dump，直接跑 npm run db:migrate 会从 0000 开始重放、与已存在的表冲突。两个选择：
    • 简单路线：生产库同样用 npm run db:push:prod 推 schema（与现在开发习惯一致），人工保证只在一处执行；
    • 规范路线：对现库做一次 baseline（把 0000–0008 标记为已应用，再启用 migrate 流程），后续升级走 db:generate → 审查 SQL → CI 里 db:migrate → 滚动重启。
  2. 首次启动顺序（seed 竞态）：ensureChannelsSeeded 的查空+插入已包在 Postgres advisory lock 里（services/admin/channels.ts），多实例并发首启不会再重复插入默认渠道。规程降级为保险动作：仍建议第一台先启动完成 seed 后再扩容。后续重启无此问题（表非空即跳过）。
  3. 升级发布时：先迁移、后滚动重启；迁移 SQL 要求向后兼容（先加列后删列、双写过渡），避免旧实例在新 schema 上崩溃。

7. 负载均衡配置

upstream mycut_app {
    least_conn;
    server 10.0.0.11:3000 max_fails=3 fail_timeout=10s;
    server 10.0.0.12:3000 max_fails=3 fail_timeout=10s;
}
server {
    listen 443 ssl;
    server_name cut.example.com;

    location / {
        proxy_pass http://mycut_app;
        proxy_set_header Host              $host;
        proxy_set_header X-Forwarded-For   $remote_addr;   # 覆写而非追加：防止客户端伪造前缀绕过限流
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_buffering      off;    # /api/media/download 是流式视频代理，不能缓冲
        proxy_read_timeout   300s;   # 下载代理长响应
        client_max_body_size 512m;   # 素材上传
    }
}
运维警示 X-Forwarded-For 的语义在本版本已变更：必须在 Nginx 上覆写该头。
即使用上面配置里的 proxy_set_header X-Forwarded-For $remote_addr;（覆写，而非默认的 append）。若保持 append 模式（$proxy_add_x_forwarded_for），限流 key 会取到 Nginx 前面最后一级代理的 IP（如果有的话）—— 所有限流按代理 IP 计数：攻击者可借此绕过限流，正常用户之间会互相挤兑窗口；审计日志的 ip 字段同样失真。上线前必须核对这一行配置。
  • X-Forwarded-For 必须由 LB 覆写（$remote_addr），代码侧 auth/request-ip.ts 取该头最后一项作为可信 IP——即使 LB 配置失误（用了 append 模式），取最后一项仍然安全。审计 ip 字段与所有限流共用该函数。
  • 多级代理（CDN → Nginx）时注意限流 key 取到的是最外层 IP，按实际链路调整 real_ip 模块。

8. 多机正确性论证（无粘性会话）

状态存放位置多机影响
登录会话Postgres（better-auth drizzle adapter）任一实例凭 cookie 查库即可，无需粘性。
管理员提权 cookie无状态 HMAC（BETTER_AUTH_SECRET，30 分钟）密钥一致 → 任一实例都能验签。
登录/接口限流Redis（滑动窗口 + better-auth secondary storage）全实例共享同一窗口，计数不会因换节点被绕过。
AI 生成任务jobId/refId 由客户端持有，轮询时服务端按 channel+job 重查密钥（api/ai/poll）提交与后续轮询落在不同实例完全正确。
点数冻结/退款Postgres 账本，(kind, refId) 幂等与实例无关。
渠道/模型配置Postgres，改动即时生效（无进程内缓存）每请求直查，任何实例修改全网立即可见。
编辑器项目/素材浏览器 IndexedDB/OPFS不经过服务器（见第 12 节限制）。

9. 滚动升级流程

  1. CI/本机构建新镜像 → 推镜像仓库（或两台机器各自 build 同一 commit）。
  2. 若本版含 schema 变更：先在一台跳板上执行迁移（第 6 节），确认向后兼容。
  3. LB 摘除 app-1（或 docker compose up -d 重建）→ 健康检查通过 → 放回流量 → 观察 /api/health 与错误日志。
  4. 同样处理 app-2。全程至少一个实例在线，用户无感。
  5. 回滚 = 把镜像 tag 换回上一版滚动一次；schema 变更需按“向后兼容”约定保证旧代码可跑。

10. 备份与恢复

对象策略恢复要点
Postgres每日 pg_dump（或托管自动备份）+ WAL 归档可选整库恢复即可。必须与 MODEL_CREDENTIALS_KEY 配套保管：库里的渠道密钥是密文，密钥丢了 = 所有渠道密钥作废，只能在管理面板逐个重填。
BETTER_AUTH_SECRET
MODEL_CREDENTIALS_KEY		密码管理器/离线保险柜各存一份换 BETTER_AUTH_SECRET 会踢掉全部登录（可接受）；MODEL_CREDENTIALS_KEY 目前没有重加密工具，等同不可换，务必不丢。
Redis不备份数据可丢（第 5 节）。
用户项目/素材不备份（在用户浏览器里）见第 12 节。

11. 安全清单（上线前逐项打勾）

  • ☐ BETTER_AUTH_SECRET 换为 32+ 字节强随机（当前开发值已被 better-auth 判定低熵）。
  • ☐ MODEL_CREDENTIALS_KEY 重新生成（勿复用开发值），生成命令见 apps/web/.env.example 内注释。
  • ☐ 全站 HTTPS；NEXT_PUBLIC_SITE_URL 为正式域名（better-auth trustedOrigins 随之生效）。
  • ☐ 管理面板依赖二次提权（30 分钟），确认生产域名下 cookie 属性正常（sameSite=lax、httpOnly）。
  • ☐ LB 正确设置 X-Forwarded-For，避免限流按 LB IP 误伤全体。
  • ☐ 测试账号（admin@mycut.test / user@mycut.test 等）不带入生产库。
  • ☐ 审计日志哨兵（writeAudit 的 U+FFFD 告警）在监控里可见。

12. 已知限制与注意事项

  • 项目数据在浏览器本地：同一用户换浏览器/换电脑/清站点数据，项目与素材不会跟随。多机部署解决的是“服务可用性”，不是“项目云同步”。若将来要做云同步，需要新增服务端项目存储与同步协议，是独立立项。
  • 限流 fail-open：Redis 挂掉时限流失效但服务可用（代码里明确注释的取舍）。对 Redis 做存活监控即可。
  • dev 级 linger：Next 16 的 proxy 层每个受保护页面请求都会查一次会话（本地库 1–3ms）。多机后这是 DB 最重的常规读，给 app.sessions（better-auth 表）保持默认索引即可，无需额外优化。
  • 单点 DB：本方案多机的是应用层；Postgres 仍是单点。起步阶段可接受，规模上来后再考虑托管高可用。
