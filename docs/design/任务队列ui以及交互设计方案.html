AI 视频生成任务队列 · UI 与交互设计方案

解决"离开生成面板即丢失生成状态"的问题：把生成过程升级为用户可见、可追踪、可回查的任务队列。
版本 v2（增补布局方案） 范围 UI / 交互 / 状态机 / 数据草案 适用 AI 视频面板 · 单任务与分镜批次 关联 ai-video.tsx · /api/ai/generate · /api/ai/poll

01背景与问题

当前生成流程完全由 AI 视频面板组件持有：提交、轮询、渠道回退、结果入库都在 ai-video.tsx + generate.ts 的组件作用域内完成。由此产生四类可感知的问题：

状态丢失切换面板即失去进度
isGenerating 等全部是组件局部 state，切到素材 / 时间线面板后组件卸载，轮询循环随之终止，用户无法再知道任务是否完成、是否失败。
无回查能力历史生成不可追溯
生成结束后只有一次性 toast / 素材入库，没有"我之前生成过什么、用了哪个渠道、花了多少点、为什么失败"的记录。
刷新即中断页面刷新任务失联
jobId、渠道信息、exclude 列表都在前端内存，刷新后客户端无法重新接上上游任务，点数已冻结却看不到结果。
批次不可见分镜多镜头缺全局视图
分镜模式串行生成 N 个镜头（"镜头 i/N"），用户只能停在面板里盯着进度文案，中途切走就不知道整体完成到第几个。

02设计目标

  • 后台可持续 — 提交后任务与面板解耦，切换任意面板、打开其他抽屉，状态都持续更新。
  • 随处可达 — 全局入口（角标计数）+ 一键打开任务队列，任何界面 1 次点击看到所有任务状态。
  • 可回查 — 每个任务保留完整档案：参数、渠道、状态时间线、失败原因、点数消耗 / 退还。
  • 可操作 — 完成后可直接预览并插入素材库 / 时间线；失败后可带原因一键重试。
  • 克制 — 不打断创作流：进行中不弹窗骚扰，完成 / 失败用轻 toast + 角标提示，详情按需展开。

03方案总览与信息架构

新增一层全局任务层（与面板解耦），由三个 UI 承载：

  • ① 入口与角标 — 左侧功能栏"AI 视频"图标与面板头部各一个入口，进行中时显示数量角标并呼吸提示；点击打开任务队列抽屉。
  • ② 任务队列抽屉（列表态）— 覆盖在编辑器右侧，分"进行中 / 历史"两组，卡片即状态；点击卡片进入详情。
  • ③ 任务详情抽屉 — 单任务的完整档案：参数、状态时间线（含渠道回退）、失败原因明细、完成预览与操作。

生成流程的归属变化：提交与轮询上收到全局任务层（配合服务端任务表），AI 视频面板只负责"发起生成"和"接收完成回调"，不再持有轮询生命周期。

06交互规格

6.1 各状态的行为约定

状态卡片展示可用操作自动行为
提交中 模型名 + 不定进度条 详情 超时 15s 未拿到 jobId → 转入失败（沿用现有提交超时）
排队中 不定进度条 + "排队中" 详情 轮询间隔 5s；>2 分钟仍排队时在详情时间线标注"上游较慢"
生成中 已用时长计时 + 进度条（无真实百分比，按模型均时估个进度，标注"预估"） 详情 完成 → 自动入库（现状逻辑）+ toast + 角标 -1
已完成 视频缩略卡 + 消耗点数 插入时间线 / 在素材库查看 / 同参数再生成 / 删除记录 结果 URL 为 7 天有效签名地址，详情内标注"请尽快下载"，素材库已有本地副本则不受影响
已失败 红色状态 + 首行原因摘要 查看明细 / 重试 / 删除记录 冻结点数自动退回并标注；toast 提示失败 + "查看原因"
已取消（二期） 灰色状态 重新生成 / 删除记录 调用上游 cancel_url，已生成部分不收费（以渠道文档为准）

6.2 关键交互规则

  • 发起生成：提交成功后面板不强制跳转，仅在面板按钮区给出轻提示（"已提交，可在任务队列查看"）；用户可立即再次发起（并发任务上限 3 个进行中，超出时按钮禁用并提示，防误刷渠道）。
  • 离开面板：进行中时切换面板 / 打开其他抽屉，不弹任何打断；左侧栏角标与 toast 承担提醒。生成与面板解耦后轮询由全局任务层持有。
  • 打开队列抽屉：进行中分组置顶并按剩余等待时间排序；历史按时间倒序；抽屉打开期间轮询间隔提升到 3s，关闭回落 8s。
  • 完成时若正停留在队列抽屉：对应卡片原地变为"已完成"并短暂高亮，不自动跳转详情。
  • 失败时：toast"生成失败：<首行原因> · 查看原因"点击直达详情；渠道明细默认折叠，避免普通用户被 400 报文淹没（F4）。
  • 重试：以原参数重新走一遍提交（新任务、新计费冻结）；"改用推荐模型重试"仅在失败原因为渠道类错误时出现，按渠道覆盖度推荐可用模型。
  • 删除记录：仅删展示记录（二次确认），不影响已入库素材；进行中任务不可删除。
  • 权限：任务按用户隔离，列表与详情都只返回本人数据（沿用现有 getSessionUser 鉴权）。

6.3 边界场景

场景行为
页面刷新 / 关闭再打开进行中任务由服务端持久化，重新打开后队列自动恢复并继续出状态（依赖 07 节的任务表 + 服务端轮询上收，为落地前置）。
登出再登录（同账号）同上，按用户维度恢复。
分镜批次中途某镜头失败批次卡片显示 n/m 完成 + 失败镜头角标；批次不自动终止，后续镜头照常；详情内逐镜头展示，失败镜头可单独重试。
渠道回退成功用户无感：状态仍是"生成中"，详情时间线多一条"渠道回退：七牛国内 → 七牛海外"。
上游 7 天签名链接过期已完成任务详情提示"原始链接已过期"；素材库本地副本仍可用（下载入库即已落本地）。
无网络 / 轮询失败状态旁标注"同步中…，上次更新 15:04"，不误报失败；恢复后自动补齐。

07数据与同步（落地前置）

要满足"刷新可恢复、离开可追踪"，任务必须落库，且"轮询 + 渠道回退"要从客户端上收到服务端。草案如下：

7.1 任务表 generation_tasks

id              text pk
user_id         text  → app.users        -- 隔离
batch_id        text?                    -- 分镜批次父 id（单任务为 null）
batch_index     int?                     -- 批次内序号
model_id        text  → app.ai_models
prompt          text
params          jsonb                    -- {mode,duration,resolution,aspect,audio,cameraMovement}
start_image     text?                    -- data URL 存对象存储（二期；一期不落）
status          text                     -- submitting|queued|generating|succeeded|failed|canceled
channel_id      text?                    -- 最终成功 / 最后尝试的渠道
protocol        text?
upstream_job_id text?
cancel_url      text?                    -- 二期取消用（提交时顺手保存）
video_url       text?
error_summary   text?                    -- 首行人类可读原因
error_details   jsonb?                   -- 各渠道尝试数组 [{channel,message,at}]
points_frozen   int                      -- 冻结点数
points_settled  int?                     -- 实扣；null 且 failed = 已退回
created_at / started_at / finished_at  timestamptz

7.2 接口与轮询上收

  • POST /api/ai/generate 改造：提交即落任务行（submitting），拿到 jobId 后补齐渠道信息转 queued；客户端改为返回 taskId。
  • GET /api/ai/tasks / GET /api/ai/tasks/:id：本人任务列表 / 详情。惰性同步（一期推荐）：读取时对 active 任务就地调 /api/ai/poll 同步上游状态、执行渠道回退与结算 / 退点，再返回最新状态——不需要独立 worker。
  • 前端：全局 TaskQueueProvider（context）持有一个 5–8s 的轮询循环调 tasks 接口，驱动角标、抽屉与 toast；AI 视频面板只消费状态并发起生成。
  • 二期可选：SSE / 长轮询推送状态变化；独立 worker 定时同步，摆脱"无人打开页面时不同步"的限制。
兼容性：现有 /api/ai/generate 的计费冻结 / 结算 / 退款、渠道路由、exclude 回退逻辑全部保留，只是执行主体从客户端循环移到服务端同步过程；分镜批次即"一次提交 N 个任务行 + 同一 batch_id"。

08分期范围

一期可见 · 可追踪 · 可回查
  • generation_tasks 表 + generate/poll 上收 + tasks 接口
  • 全局 TaskQueueProvider、角标、队列抽屉、详情抽屉
  • 六状态机、失败原因与渠道明细、退点标注、重试
  • 分镜批次聚合展示
  • 刷新 / 重开恢复
二期可控性 · 体验增强
  • 取消任务（cancel_url 已在提交时保存）
  • 状态推送（SSE）替代前端轮询
  • 起始帧落对象存储，配合 MiniMax 公网图限制
  • 历史搜索 / 按模型筛选、导出记录
  • 队列并发上限可配置（管理面板）
开放问题：① 生成结果是否保留"自动插入素材库"默认行为，还是改为完成后由用户手动入库（影响磁盘占用与计费感知）；② 失败记录保留时长（建议 30 天随清理策略）；③ 并发上限数值（建议进行中 3、每日上限沿用模型 dailyLimit）。

09布局位置备选方案（v2 增补）

一期实现采用了"右侧全高抽屉"（见 05 节 F2）。实测发现两个问题：遮挡属性面板与导出按钮区、全高形态对"瞄一眼进度"这种高频轻需求来说过重。本章给出 5 个布局位置的备选，可单独采用，也可组合（如 C + D）。 所有方案共享同一份任务数据与状态机（04 节），仅容器不同——切换成本低。

方案 A 右侧全高抽屉（一期现状） 基线

覆盖编辑器整个右缘（含头部导出区下方至时间轴上缘），列表 + 详情两级。

优点空间充裕：详情、时间线、渠道明细都能完整展开；与属性面板同侧，阅读动线一致；一期已实现，零改造。
实测问题遮住属性面板与导出按钮；全高形态对"瞄一眼"过重；打开时必遮挡，无法与参数调节并存。
方案 B 属性区宽度的中部抽屉（改良现状） 保守改良

仍是右缘抽屉，但不再全高：顶部从编辑器头部之下开始、底部到时间轴上缘为止，宽度与属性面板一致（约 300px）。头部导出区与时间轴完全不被遮挡。

方案遮挡随手可见详情承载改造量适用
A 右侧全高抽屉（现状）大（属性+导出区）需点开最好无仅详情场景
B 中部抽屉中（属性）需点开好小想保留现状形态时
C 底部任务坞无始终可见中（浮层承载）中进行中状态的日常跟踪
D 面板"任务"标签页无切 tab 后需召回中（窄面板）中历史回查 / 批次管理
E 头部下拉小（局部浮层）全局中中编辑器外页面复用（二期）
推荐组合：C + D。方案 C（任务坞）承载"进行中的实时跟踪"——编辑时永远看得见、零遮挡；方案 D（任务标签页）承载"历史与批次管理"——任务有固定的家，信息架构成立。一期已有的右侧全高抽屉退役为"详情浮层"的实现细节（点 chip / 卡片后的展开层，宽度自适应）。角标（左栏 + AI 视频面板头部）在两种方案下都保留。
切换成本：五个方案共享 useTaskQueue() 的同一份数据与动作（提交 / 列表 / 详情 / 删除 / 批次插入），差异只在容器组件——选定后约一天内可完成迁移，且随时可再换。
